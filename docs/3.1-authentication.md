# Authentication

Catalogi uses OpenID Connect (OIDC) for authentication, allowing you to connect to any OIDC-compliant identity provider.

## How It Works

Catalogi implements the standard OIDC Authorization Code Flow:

1. User clicks login
2. Application redirects to identity provider
3. User authenticates with the provider
4. Provider redirects back with authorization code
5. Application exchanges code for tokens
6. User is authenticated

The implementation uses automatic OIDC discovery via `/.well-known/openid-configuration`, making it compatible with any standard OIDC provider.

## Required Environment Variables

To configure authentication, you need to set the following environment variables. All of them are required by the API at startup, except `CATALOGI_INITIAL_ADMIN_EMAIL`:

| Variable                       | Description                                                                 | Example                                            |
| ------------------------------ | --------------------------------------------------------------------------- | -------------------------------------------------- |
| `OIDC_ISSUER_URI`              | The OIDC provider's issuer URL (without `.well-known/openid-configuration`) | `https://auth.example.com/realms/my-realm`         |
| `OIDC_CLIENT_ID`               | Your application's client ID registered with the provider                   | `catalogi`                                         |
| `OIDC_CLIENT_SECRET`           | Your application's client secret                                            | `secret-value-here`                                |
| `OIDC_MANAGE_PROFILE_URL`      | URL where users can manage their profile                                    | `https://auth.example.com/realms/my-realm/account` |
| `APP_URL`                      | Your Catalogi application URL (used for redirect URIs)                      | `http://localhost:3000`                            |
| `CATALOGI_INITIAL_ADMIN_EMAIL` | OIDC email allowed to become the first Catalogi administrator (optional)    | `admin@example.com`                                |

## Initialize the first Catalogi administrator

Catalogi does not create a local account or password. Configure your OIDC provider first, set `CATALOGI_INITIAL_ADMIN_EMAIL` to the intended administrator's OIDC email address, start Catalogi, and sign in with that address. The comparison is case-insensitive. The user is promoted only if no Catalogi administrator exists; every other new user receives the `user` role.

After the first administrator has signed in successfully, you may remove the variable. Passwords, password changes, multi-factor authentication, and other credential policies remain entirely managed by the OIDC provider. If the variable is absent and no administrator exists, the public application still starts and logs an explicit warning with these initialization instructions.

## Redirect URIs to Configure

When registering your application with the identity provider, you need to configure these redirect URIs:

- **Login callback**: `${APP_URL}/api/auth/callback`
- **Logout callback**: `${APP_URL}/api/auth/logout/callback`

For example, if `APP_URL=http://localhost:3000`:

- Login callback: `http://localhost:3000/api/auth/callback`
- Logout callback: `http://localhost:3000/api/auth/logout/callback`

## Required OIDC Scopes

The application requests the following standard OIDC scopes:

- `openid` - Required for OIDC
- `email` - To get user email
- `profile` - To get user profile information

For AgentConnect/ProConnect, additional scopes are automatically added:

- `given_name`
- `usual_name`

## Configuration Example

### Keycloak

Keycloak is an open-source identity and access management solution used as reference example.

```bash
OIDC_ISSUER_URI=http://localhost:8080/realms/catalogi
OIDC_CLIENT_ID=catalogi
OIDC_CLIENT_SECRET=your-client-secret
OIDC_MANAGE_PROFILE_URL=http://localhost:8080/realms/catalogi/account
APP_URL=http://localhost:3000
CATALOGI_INITIAL_ADMIN_EMAIL=admin@example.com
```

See [Setting up Keycloak](3.2-setup-a-keycloak.md) for detailed Keycloak setup instructions.

## Other OIDC Providers

Any OIDC-compliant provider should work (Keycloak, AgentConnect, ProConnect, Auth0, Okta, Google, Azure AD, etc.) as long as it:

1. Provides a `/.well-known/openid-configuration` discovery endpoint
2. Supports the Authorization Code flow
3. Provides standard `openid`, `email`, and `profile` scopes
4. Returns user information with at least `sub` and `email` claims

Generic configuration:

```bash
OIDC_ISSUER_URI=https://your-provider.com
OIDC_CLIENT_ID=your-client-id
OIDC_CLIENT_SECRET=your-client-secret
OIDC_MANAGE_PROFILE_URL=https://your-provider.com/account
APP_URL=http://localhost:3000
```

## Security

**Production requirements**:

- Use HTTPS for `APP_URL`
- Keep `OIDC_CLIENT_SECRET` secure
- Sessions use HTTP-only cookies, Secure outside development and whenever `APP_URL` uses HTTPS (7-day cookie lifetime; server-side token expiry and refresh still apply)
- Tokens stored server-side only

## Browser binding of login transactions

`/api/auth/login` generates an independent random `state` (32 bytes) and a random session UUID. The UUID is placed in the temporary `oidcTransaction` cookie, never in the authorization URL. This cookie is HttpOnly, host-only, Secure outside development and whenever `APP_URL` uses HTTPS, and SameSite=Lax to support the identity provider's top-level GET callback. Its path is the public `${APP_URL}` path followed by `/api/auth`, and its lifetime is 10 minutes.

Before exchanging any code, the callback atomically matches the cookie UUID and the state against an unauthenticated, non-logged-out session created less than 10 minutes ago. The database update clears the state to mark the transaction consumed. Concurrent requests cannot both consume it. Authenticated sessions cannot be reused as pending transactions. This uses existing columns and requires no schema migration.

On success, the temporary cookie is deleted with the same path and cookie attributes, the local profile and roles follow the usual authentication workflow, and the final `sessionId` cookie is installed. An invalid, expired, missing, mismatched, or replayed transaction returns a generic HTTP 400 without changing either cookie or the current authenticated session. Keeping the temporary cookie on rejection allows a newer legitimate login in another tab to finish; the cookie otherwise expires naturally. Internal/provider failures return a generic HTTP 500 and clear the temporary cookie. A consumed transaction stays consumed even after failure: restart login to retry. Codes, states, and tokens are not included in these responses or the request logger. Internal failures emit a fixed `OIDC authentication failed` error log with `stage: login` or `stage: callback`; the original exception and request data are never passed to this log. Invalid callbacks (HTTP 400) do not emit this internal-error signal.

Tabs share this cookie: **the last login started wins**. An older tab's callback is rejected without clearing the newer tab's transaction. Independent browser contexts have separate cookies and cannot consume each other's callback. A login already being processed by the server is not cancelled by opening another tab.

Regression tests cover the use case with PostgreSQL (including concurrent consumption), the HTTP routes and cookie attributes, and two isolated Chromium contexts against Keycloak (`e2e/tests/oidc-browser-binding.spec.ts`). Database tests accept `TEST_DATABASE_URL` to target an isolated test database.

## Upgrading existing deployments

No database migration, new environment variable, or identity-provider redirect URI change is required. Existing authenticated sessions remain valid. Logins started before the upgrade lack the temporary cookie and must be restarted from the login button.

Keep `APP_URL` set to the public browser URL and route `${APP_URL}/api/auth/*` to the API as in the supplied proxy examples. Cookies require HTTPS unless `IS_DEV_ENVIRONNEMENT=true` and `APP_URL` uses HTTP; the development flag never disables Secure for an HTTPS URL.

Custom frontends and authentication scripts must start login and follow the callback using the same browser context or cookie jar. Preserve the `oidcTransaction` cookie between those requests. Passing only `code` and `state` to the callback is intentionally no longer supported. Direct consumers of `handleAuthCallback` must also provide the cookie value as `transactionId`.

Update all API replicas: old replicas continue to accept unbound callbacks until they are replaced. During a rolling deployment, a login initiated on an old replica can be rejected on a new one; restart that login after the rollout completes. An HTTP 400 leaves any existing authenticated session intact.
